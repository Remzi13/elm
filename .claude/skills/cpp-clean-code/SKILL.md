# C++ Clean Code в elm

Цель: код, который легко прочитать, проверить и изменить. Не «умный» код, а очевидный.

Этот файл о том, как принимать решения. Сущности, модули, потоки и стиль описаны в `CLAUDE.md`. Если правила расходятся, прав `CLAUDE.md`, а если и он расходится с принятым в проекте стилем, прав проект.

## Порядок приоритетов

Когда правила конфликтуют, решай в таком порядке:

1. **Корректность:** код делает то, что нужно, без UB, и не нарушает границы потоков и модулей.
2. **Простота (KISS):** самое простое решение, которое работает.
3. **Явность:** всё, что происходит, видно в месте вызова.
4. **Читаемость:** намерение видно из имён и структуры.
5. **Отсутствие дублирования (DRY):** но не ценой неверной абстракции и не ценой явности.
6. **Производительность:** только там, где это подтверждено замером (Tracy, окно Profiler).

## Меньше кода

- Из двух решений выбирай то, где меньше кода и новых имён.
- Функция или метод с одним вызовом не нужны, пиши код на месте. Выносить можно, только если иначе функция нарушит лимиты раздела 3 `CLAUDE.md`.
- Чем базовее подсистема, тем меньше в ней кода. `core` и `math` дают минимум операций, а готовые сценарии живут у клиента: он лучше знает, что ему нужно.
- Обёртки для удобства над существующим API не добавляй. Новый публичный метод появляется, только когда задача без него не решается.

## Явное лучше неявного

Не прячь в одну функцию создание объекта, его работу и передачу данных дальше. Статический метод, который внутри создаёт объект и тут же его уничтожает, отбирает решение у клиента.

```cpp
// Плохо: не видно, что файл открывается, читается и закрывается
auto text = File::ReadText(path);

// Хорошо: клиент видит все шаги и сам решает, что делать с ошибками и данными
File file;
if (auto opened = file.Open(path, FileMode::Read); !opened)
    return UnexpectedSerializationError(opened.error().message, LogSource);
const auto block = file.ReadAll();
```

Там, где есть общепринятый способ, бери его и не изобретай свой: файл открывают вызовом `Open(path, mode)`, как в `fopen` и `std::fstream`.

## KISS

- Выбирай очевидное решение, а не изящное. Если для понимания строки нужен комментарий «как это работает», упрости строку.
- Два `if` с ранним возвратом лучше тернарного оператора, который собирает `EngineResult` из ошибки.
- Свободная функция лучше класса, если нет состояния и инвариантов. Класс только со статическими методами не создавай.
- Обычный `if`/`switch` лучше полиморфной иерархии, если вариантов мало и они не расширяются извне.
- Шаблоны только когда нужна обобщённость для нескольких типов, которые уже есть, и с ограничением через `concepts`.
- Не вводи паттерны (Factory, Visitor, Observer, Singleton) «на будущее».

```cpp
// Плохо: интерфейс, фабрика и реестр ради одного формата
class IModelExporter { /* ... */ };
class ModelExporterFactory { /* ... */ };

// Хорошо: один формат, одна функция
auto ExportGltf(const Scene& scene, const Path& path) -> EngineResult<void>;
```

## YAGNI

- Не добавляй параметры, флаги, настройки и точки расширения, которых никто не использует.
- Абстракция (интерфейс `I*`, базовый класс, шаблон) появляется, когда есть **минимум две** реальные реализации.
- Удаляй мёртвый код и закомментированные блоки: их хранит git.

## SRP

У функции и класса одна причина для изменения. Проверочный вопрос: «Опиши, что делает эта сущность, одним предложением без союза „и“». Если не получается, раздели.

Окна (`*Window`) показывают и правят, системы (`*System`) считают, `resource` читает и пишет файлы, компоненты остаются данными без логики.

Признаки нарушения:
- в имени есть `And`, `Manager`, `Helper`, `Utils`, `Processor` без уточнения;
- класс одновременно работает с файлами, логикой и UI;
- функция больше 30 строк, глубже 3 уровней вложенности или с параметрами больше 4;
- класс с десятком несвязанных методов.

## DRY без фанатизма

- Выноси общий код после **третьего** повторения, не раньше.
- Небольшое дублирование лучше неправильной общей абстракции.
- Повтор шагов `File` у клиентов это не дублирование знания: они явные, и каждый клиент сам решает, что делать с ошибкой.
- Одно знание в одном месте: константы, форматы, правила проверки.

## Функции

- Короткие и с одной задачей. Ранний `return` вместо глубокой вложенности.
- Возвращай результат, а не пиши в out-параметры.
- Входные параметры: дешёвые типы и хэндлы по значению, остальное по `const T&`, строки как `StringView`, массивы как `std::span`.
- Без булевых флагов, меняющих поведение: `Render(true)` нечитаемо, сделай две функции или `enum class`.

```cpp
// Плохо
void ParseVersion(const String& text, int& version, bool& ok);

// Хорошо
[[nodiscard]] std::optional<int> ParseVersion(StringView text);
```

## Классы

- Значимые типы следуют правилу нуля. Системы с идентичностью (`*System`, `Game`, `Editor`) запрещают копирование и перемещение.
- Конструкторы с одним аргументом `explicit`, в наследниках `override` или `final`.
- Композиция вместо наследования. Наследование только для «является».
- `struct` для данных без инвариантов (компоненты, `*Desc`), `class` с полями `private`, когда инвариант надо защищать.

```cpp
class Document {
public:
    explicit Document(String title)
        : m_title(std::move(title))
    {
    }

    void AddPage(Page page);

private:
    String m_title;
    Vector<Page> m_pages;
};
```

## Ресурсы и память

- RAII для всего: память, файлы, мьютексы, ресурсы рендера.
- Контейнеры и указатели из `core/Std.hpp`: `String`, `Vector`, `MakeUnique`, `MakeShared`. Голых `new`/`delete` и `malloc`/`free` нет.
- `UniquePtr` по умолчанию, `SharedPtr` только при реально разделяемом владении.
- Ссылка для обязательного невладеющего доступа, указатель для необязательного. Ссылка, живущая дольше одной операции, это хэндл.
- Файлы только через `File`, без `std::ifstream` и `std::ofstream`.

## const и типы

- `const` везде, где значение не меняется, `[[nodiscard]]` на всём, что возвращает результат.
- Именованные константы вместо магических чисел и `#define`. `enum class` вместо `int`-кодов, отдельный тип вместо `std::pair` или голого `int`.
- Только именованные касты.
- `auto`, когда тип очевиден из правой части.

## Обработка ошибок

- Операция, которая может не выполниться, возвращает `EngineResult<T>`, ошибка создаётся через `MakeUnexpected`. Ожидаемое отсутствие: `nullptr`, `std::optional`, `false`.
- Исключения только для ошибок Lua. Результат не игнорируй и не глуши ошибки пустым `catch (...) {}`.
- Предусловия проверяй на границах модуля, инварианты через `ELM_ASSERT`.

## Имена

- Имя объясняет **зачем**, а не **как**: `activeNodes`, а не `vec2`. Имена сущностей бери из глоссария `CLAUDE.md`, без синонимов.
- Методы и свободные функции `PascalCase` с глагола, булевы как вопрос (`IsValid`, `HasBody`), поля `m_camelCase`, поля `struct` `camelCase`, в Lua `snake_case`.
- Длина имени пропорциональна области видимости: `i` в коротком цикле нормально, в поле класса нет.

## Красные флаги

| Признак | Принцип | Что делать |
|---|---|---|
| Сложное решение простой задачи | KISS | Переписать прямолинейно |
| Функция с одним вызовом | Меньше кода | Написать на месте |
| Статический метод создаёт объект и сам его уничтожает | Явность | Отдать объект клиенту |
| Обёртка для удобства в `core` или `math` | Базовая подсистема | Оставить сценарий у клиента |
| Интерфейс с одной реализацией | YAGNI | Убрать интерфейс |
| Неиспользуемые параметры, флаги, ветки | YAGNI | Удалить |
| «God class», `Manager`, `Utils` | SRP | Разделить по причинам изменения |
| Функция больше 30 строк, вложенность больше 3 | SRP | Ранний `return`, потом вынести часть |
| Голый `new`/`delete` | RAII | `MakeUnique` или контейнер |
| Out-параметры | Функции | Вернуть значение, `std::optional` или `struct` |
| Копипаста знания в трёх местах | DRY | Вынести в одно место |

## Как рефакторить существующий код

1. Сначала прочитай модуль и его заметку в `docs/`. Проверь, что покрывают `elm_tests` и `editor --editor-selftest`.
2. Меняй **поведение и структуру раздельно**: рефакторинг не меняет результат программы.
3. Маленькие шаги: одно изменение, одна понятная причина.
4. Если тестов нет, предложи тест на текущее поведение. Рендер и большая часть UI проверяются запуском, и об этом надо писать прямо.
5. Постороннее без запроса не рефактори, публичный API не меняй без согласия пользователя.
6. В ревью объясняй каждое замечание через принцип: «нарушает SRP: окно и считает, и пишет в файл».

## Чек-лист перед завершением

- [ ] Каждую функцию и класс можно описать одним предложением без «и»
- [ ] Нет функций с одним вызовом, обёрток для удобства и абстракций с одной реализацией
- [ ] Создание объекта и его работа видны в месте вызова
- [ ] Нет мёртвого и закомментированного кода
- [ ] Функции короткие, параметров мало, out-параметров нет
- [ ] `const` расставлен, магических чисел нет, имена объясняют назначение
- [ ] Сборка без новых предупреждений, изменённые файлы прошли `clang-format -i`
- [ ] `elm_tests` и `editor --editor-selftest` проходят, `docs/` обновлены
