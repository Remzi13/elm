# Системы (черновик дизайна)

> Переделка идёт по шагам ([[#Порядок переделки]]), сделанное отмечено ✅; как устроено сейчас — [[Проекты#Плеер]].
> Имена систем — по модулям, см. [[#Понятия]].

## Зачем

До переделки `Engine` был одним объектом со всеми системами внутри. Программа получала их геттерами, окна
редактора — широким `ImGuiWindowContext` или ссылками, сохранёнными при создании. Отсюда:

- **связность:** кто подключил `Engine.hpp`, знает все подсистемы; окну логов приходят сцена и рендер;
- **владение размыто:** режимы (`PlayMode`, `EditMode`), менеджеры (`ModelManager`) и шаги кадра лежат на одном
  уровне с системами;
- **время жизни** держится на договорённости (окна проекта закрываются раньше проекта);
- **кто и когда меняет данные**, нигде не записано: окна правят сцену посреди отрисовки UI;
- **потоки:** гонок нет только потому, что всё на update-потоке, но это не проверяется.

Цель: несколько крупных систем, у каждой одна обязанность и узкий фасад; программа (`elm`, `editor`) сама
создаёт свой набор и сама ведёт кадр; зависимости видны в конструкторах и проверяются при компиляции.

Сознательно **без** реестра систем, общего интерфейса систем и планировщика фаз: наборы систем известны при
компиляции, программ две, а явный код читается лучше выведенного порядка (см. [[#Чего нет и почему]]).

## Понятия

| Понятие | Что это |
|---|---|
| **система** | крупная область с одной обязанностью: платформа, ресурсы, сцена, физика, скрипты, графика. Обычный класс своего модуля, своими данными владеет сама, наружу даёт узкий фасад |
| **часть системы** | класс внутри системы: модели у ресурсов, `PlayMode` у скриптов, `OcclusionCulling` у графики. Снаружи не виден, другие системы к нему не обращаются |
| **программа** | `elm` (`Game`) или `editor` (`Editor`): корень композиции. Создаёт системы полями, передаёт им зависимости в конструкторах, ведёт кадр явной функцией |
| **инфраструктура** | `core`: потоки, файлы, структуры данных, `Settings`, лог, `JobSystem`. Ниже систем, о системах не знает |

Система — это то, о чём можно сказать «за X отвечает она», и у X нет второго ответчика. Режимы, менеджеры и
шаги кадра — части, а не системы.

**Имена по модулям.** Система называется по своему модулю: `PlatformSystem` — `platform`, `ResourceSystem` —
`resource` (бывший `resmgr`, переименован), `SceneSystem` — `Scene`, `PhysicsSystem` — `physics`, `ScriptSystem` — `script`,
`GraphicsSystem` — `graphics`. Суффикс `System` только у систем; части его теряют:

| Сейчас | Станет | Чья часть |
|---|---|---|
| `render::RenderSystem` | `render::Render` (сделано) | `GraphicsSystem` |
| `InputSystem` | `Input` (сделано) | `PlatformSystem` |
| `OcclusionCullingSystem` | `OcclusionCulling` (сделано) | `GraphicsSystem` |
| `DebugDrawSystem` | `DebugDrawing` (сделано) | `GraphicsSystem` |
| `ScriptSystem` (Lua и части скриптов) | ядро системы `ScriptSystem`, к нему добавлен `PlayMode` (сделано) | `ScriptSystem` |
| `PhysicsSystem` (Jolt) | система как есть | `PhysicsSystem` |
| модуль `resmgr` | модуль `resource` (сделано) | `ResourceSystem` |


## Системы

| Система | Обязанность | Части (внутри) | Зависимости (конструктор) |
|---|---|---|---|
| `PlatformSystem` | связь с ОС: окно и ввод | `platform::Window`, `Input` (нынешний `Input`, модуль `input`), оси и действия | `Settings&` |
| `ResourceSystem` | открытый проект и загруженные ресурсы: что загружено, откуда и сколько живёт | `Project`, `ModelCatalog` (модели на CPU, хэндлы, файлы), чтение проекта и стартовой сцены (`Serializer`) | — |
| `SceneSystem` | сцена: узлы, компоненты, мировые трансформы | `Scene`, пересчёт трансформов, сцена из файла (`Append`), снимок (`SceneSnapshot`) | `ModelCatalog&` — каталог ресурсов, не вся `ResourceSystem` |
| `PhysicsSystem` | тела, шаг, запросы, столкновения | Jolt, журнал кадра | `SceneSystem&` |
| `GraphicsSystem` | всё отображение: вид, видимость, модели и отладка в кадр, показ, render-поток | `render::Render` (нынешний `RenderSystem`: устройство, ресурсы GPU, свой поток), GPU-меши моделей, камера вида и вьюпорт, `OcclusionCulling`, запись моделей, `DebugDrawing` (нынешний `DebugDrawSystem`, по опции), показ вида на всё окно | `Settings&`, `PlatformSystem&`, `const SceneSystem&`, `const ResourceSystem&` |
| `ScriptSystem` | игровая сессия на скриптах: Play/Stop, Lua, главный модуль, скрипты сущностей, игровое время | Lua-машина и части нынешнего `ScriptSystem` (модули, hot reload, скрипты сущностей, консоль), `PlayMode`, биндинги | `Settings&`, `ScriptDeps` (сцена, физика, ресурсы, ввод, камера вида, отладка) |

Редактор добавляет свои части прямо в программу `Editor`: `EditMode`, `EditorCamera`, `SceneEdits`, `EditorUi`.
Отдельной «системы редактора» нет: программа-редактор и есть её владелец.

**Только читаешь — получаешь `const&`.** Графика получает `const SceneSystem&` и `const ResourceSystem&`: писать в
сцену и ресурсы она не может по типу. Неконстантную ссылку на сцену получают только писатели: скрипты,
`EditMode`, `SceneEdits`.

**Граф без циклов:** платформа и ресурсы — внизу; сцена → ресурсы; физика → сцена; графика → платформа, сцена,
ресурсы; скрипты → сцена, физика, ресурсы, платформа, графика. Для этого `ModelManager` делится:
модель на CPU — ресурс, её GPU-копия — часть графики. Графика заводит меш при первой отрисовке модели и
удаляет, когда модели нет в ресурсах; ресурсы о GPU не знают. Поэтому ресурсы и сцена работают без рендера —
в `elm_tests` и в будущем на сервере.

`GraphicsSystem` живёт в модуле `graphics`; модуль `render` с `render::Render` — её нижняя часть, другие
системы `render` напрямую не видят.

## Программа: системы — поля, кадр — функция

Порядок полей задаёт порядок создания, разрушение идёт в обратном порядке само.

```cpp
// engine/Game.hpp — программа elm
class Game {
public:
    explicit Game(const GameDesc& desc);
    [[nodiscard]] auto OpenProject(const Path& folderOrFile) -> EngineResult<void>;
    void Run();

private:
    /// False when the game ends: the window closed or the scripts stopped it.
    [[nodiscard]] bool RunFrame(const FrameTime& time);

    Settings m_settings;
    PlatformSystem m_platform;
    ResourceSystem m_resources;
    SceneSystem m_scene;
    PhysicsSystem m_physics;
    GraphicsSystem m_graphics;
    ScriptSystem m_scripts;
    FrameClock m_clock;
};

Game::Game(const GameDesc& desc)
    : m_platform(m_settings, desc.window)
    , m_resources(m_settings)
    , m_scene(m_resources.GetModels())
    , m_physics(m_scene)
    , m_graphics(m_settings, m_scene, m_resources.GetModels())
    , m_scripts(m_settings, { .scene = m_scene, .physics = m_physics, .resources = m_resources,
          .input = m_platform.GetInput(), .camera = m_graphics.GetViewCamera(), .debugDraw = m_graphics.GetDebugDraw() })
{
}

bool Game::RunFrame(const FrameTime& time)
{
    m_platform.PollEvents();
    m_physics.BeginFrame();
    // No Edit mode to go back to: Stop ends the game
    if (m_scripts.ApplyPlayRequest() == PlayState::Stopped)
        return false;
    for (const float step : m_clock.FixedSteps(time)) {
        m_physics.Step(step);
        m_scripts.FixedUpdate(step, m_physics.GetCollisions());
    }
    m_platform.DispatchInput();
    m_scripts.Update(time);
    m_scene.UpdateTransforms();
    m_graphics.Cull();

    render::FrameWriter frame = m_graphics.BeginFrame();
    m_graphics.DrawWorld(frame);
    m_graphics.PresentToWindow(frame, m_platform.GetFramebufferSize());
    m_graphics.EndFrame(frame);
    return !m_platform.ShouldClose();
}
```

Редактор — те же шесть систем и свои части:

```cpp
class Editor {
    // ... те же системы, что у Game, в том же порядке ...
    EditMode m_editMode { m_scene, m_scripts };                    // снимок вокруг Play
    EditorCamera m_camera { m_graphics.GetViewCamera(), m_platform.GetInput() };
    SceneEdits m_edits { m_scene };                                 // правки пользователя с undo
    EditorUi m_ui;                                                  // ImGui и окна
};

bool Editor::RunFrame(const FrameTime& time)
{
    m_platform.PollEvents();
    m_physics.BeginFrame();
    ApplyProjectRequest();                 // смена проекта, см. ниже
    m_editMode.ApplyPlayRequest();         // снимок до Play, возврат после Stop
    for (const float step : m_clock.FixedSteps(time)) {
        m_physics.Step(step);
        m_scripts.FixedUpdate(step, m_physics.GetCollisions());
    }
    m_platform.DispatchInput();
    m_camera.Update(time, m_scripts.IsPlaying());
    m_scripts.Update(time);
    m_scene.UpdateTransforms();
    m_graphics.Cull();

    render::FrameWriter frame = m_graphics.BeginFrame();
    m_graphics.DrawWorld(frame);
    m_ui.Draw(frame);                      // окна читают сцену этого кадра
    m_graphics.EndFrame(frame);
    return !m_platform.ShouldClose();
}
```

Порядок кадра каждой программы читается сверху вниз в одной функции. `elm_tests` собирает свой частичный
набор (ресурсы, сцена, физика, скрипты) без платформы и графики.

## Как системы общаются

1. **Зависимость в конструкторе.** Система получает то, без чего не работает, ссылкой при создании и держит
   её до своего разрушения: зависимость создана раньше и разрушится позже. `const&` — только чтение.
2. **Данные через фасад.** Основной поток кадра — данные: физика → сцена → culling → кадр. Кто пишет, видно
   по неконстантной ссылке; когда — по функции кадра программы.
3. **Последовательность в программе вместо событий.** Многошаговые переходы (смена проекта, Play/Stop) —
   явный код программы, а не подписчики:

   ```cpp
   auto Editor::SwitchProject(const Path& file) -> EngineResult<void>
   {
       auto project = ResourceSystem::ReadProject(file);   // сначала прочитать: при ошибке остаётся старый
       if (!project)
           return MakeUnexpected(project.error());
       m_editMode.Stop();
       m_ui.CloseProjectWindows();          // окна раньше данных, на которые они смотрят
       m_edits.Clear();                     // шаги истории — про узлы уходящей сцены
       m_scripts.EndProject();
       m_physics.Clear();
       m_scene.Clear();
       m_resources.Open(std::move(*project));
       m_scripts.StartProject(*m_resources.GetProject());
       m_ui.OpenProjectWindows(*m_resources.GetProject());
       return { };
   }
   ```

   События — только для настоящей развязки, когда отправитель не должен знать получателей; сейчас таких
   случаев нет, кроме уже существующих `CollisionEvent` (их физика отдаёт скриптам в функции кадра).
4. **Запросы владельцу.** Запросы из Lua и окон (Play/Stop, открыть проект) копятся у владельца и
   применяются программой в известной точке кадра — как сейчас `PlayMode::GetRequest`/`ApplyRequest`.

## Правки сцены из редактора

> Сделано иначе, чем описано ниже (шаг 6 в [[#Порядок переделки]]): окна по-прежнему правят сцену сами, а
> `SceneEdits` находит правку вокруг кадра UI — сравнивает выбранный узел до и после и следит за
> `Scene::StructureRevision`. Модель шагов, объединение жеста и судьба истории — как здесь. Текст ниже — исходный план.

`SceneEdits` применяет правку пользователя **сразу** и записывает её для undo/redo. Задержки в кадр нет:
окна и сцена на одном update-потоке. Скрипты пишут в сцену через `SceneSystem` напрямую — undo нужен
только правкам пользователя.

### Шаг истории — команда с «до» и «после»

Шаг хранит, что было и что стало, по хэндлу узла: `SetLocalTransform { node, before, after }`,
`SetComponent<T> { node, before, after }`, `RemoveNode { node, removed }` (копия узла с компонентами и его
`NodeId`). Undo применяет `before`, redo — `after`. Новая правка после undo очищает redo. Глубина истории
ограничена (как `MaxUndoSteps = 100` в Model Editor), самый старый шаг выпадает.

Для `RemoveNode` сцене нужно уметь вернуть узел с прежним `NodeId` — то же, что уже делает
`SceneSnapshot::Restore`. Без этого undo удаления сломал бы все хэндлы на узел (выбор, ссылки в компонентах).

### Непрерывная правка — один шаг на жест

Пока пользователь тянет `DragFloat3` или ручку гизмо, правка приходит каждый кадр. В историю она должна
попасть одним шагом: «до» — значение в начале жеста, «после» — в конце. Приём тот же, что в Model Editor
(`ModelEditorWindow::RecordUndo(key, continuous)`):

- правка помечается **ключом** — что именно меняется: `{ node, EditTarget::Transform }`,
  `{ node, EditTarget::Component(ComponentType::Collider) }`;
- непрерывная правка с тем же ключом, пока **жест не кончился**, не добавляет шаг, а обновляет `after`
  верхнего шага; `before` остаётся от начала жеста;
- жест кончается, когда в UI ничего не активно. `SceneEdits` про ImGui не знает: `EditorUi` в начале кадра
  сообщает `m_edits.SetGestureActive(ImGui::IsAnyItemActive())`, гизмо — пока тянут ручку. Как в Model Editor:
  `m_editInProgress = m_editInProgress && ImGui::IsAnyItemActive()`;
- другой ключ, отпущенный жест или undo/redo начинают новый шаг.

```cpp
void SceneHierarchyWindow::DrawTransform(NodeId node)
{
    const Scene::Node* found = m_deps.scene.Find(node);
    if (!found)
        return;                        // узел удалён: хэндл устарел
    Transform transform = Transform::FromMatrix(found->localTransform);
    if (ImGui::DragFloat3("Position", &transform.position.x))
        m_deps.edits.SetLocalTransform(node, transform.ToMatrix(), EditFlow::Continuous);
}
```

Разовые правки (галка Visible, выбор модели, удаление узла) идут с `EditFlow::Single`: каждая — свой шаг.
Ввод текста в поле — тоже непрерывная правка: имя узла, набранное по буквам, — один шаг.

### Судьба истории

| Событие | История | Почему |
|---|---|---|
| **Play** | заморожена: правки в Play применяются к играющей сцене, но в историю не пишутся; undo/redo недоступны | Stop всё равно вернёт сцену как до Play; шаг истории про узел, созданный игрой, после Stop потерял бы смысл |
| **Stop** | та же, что до Play | `EditMode` возвращает снимок с прежними `NodeId`: шаги истории снова указывают на свои узлы |
| **смена проекта** | очищается | сцена и модели проекта уходят, хэндлы шагов больше ничего не значат. Шаг `SwitchProject`: `m_edits.Clear()` рядом с `m_ui.CloseProjectWindows()` |
| **замена сцены** (открыть другой файл сцены, новая сцена, тестовая сцена `--scene`) | очищается | шаги относятся к узлам прежней сцены |
| **сохранение сцены** | сохраняется | файл не меняет узлы; `SceneEdits` запоминает шаг, на котором сохранили, — по нему же видно, есть ли несохранённые правки (замена нынешнего `Scene::Revision()` для признака «изменено») |

## Окна редактора

Окно получает только своё — структуру зависимостей, которую собирает `Editor` при создании окна. Ни систем,
ни `Editor` окно не видит; общего `ImGuiWindowContext` нет.

```cpp
/// Valid while the window lives: Editor destroys project windows before the project closes.
struct SceneHierarchyDeps {
    const Scene& scene;
    SceneEdits& edits;
    const ModelCatalog& models;
    const ScriptInspection& scripts;
    Selection& selection;              // вместо SelectedSceneInstance в MessageBus (сделано)
};
```

Окно логов получает только лог, профайлер — только статистику. Связи между окнами (выбранный узел,
режим Play, открыть файл) — сервисы редактора (`Selection`, `script::PlayRequests`, `FileOpener`), которые `Editor`
передаёт тем окнам, кому они нужны; `MessageBus` уходит. Пока нет `SceneEdits` (шаг 6), Scene Hierarchy получает
неконстантную `Scene&` и правит сцену сама.

## Потоки

- Системы и их фасады — update-поток, входы помечены `ELM_ASSERT_THREAD(Update)`.
- `GraphicsSystem` единственная с потоком: render-поток её части `render::Render`. Связь с ним — только
  снимок кадра (`FrameWriter` → `FrameSnapshot` → `FrameRing`) и команды ресурсов. Отпущенные поверхности UI —
  счётчик (`GetReleasedSurfaceCount`).
- Параллельно внутри своего шага: culling (`parallelFor`) и шаг физики. Снаружи шаг синхронный: когда метод
  вернулся, работа закончена.
- Изменяемых данных, которые два потока трогают одновременно, нет; мьютексы только внутри очередей передачи.
- Шаг физики идёт на воркерах `core::JobSystem`: задачи Jolt ставит адаптер `JPH::JobSystemWithBarrier`
  (`CoreJobSystem` в `PhysicsSystem.cpp`), своего пула потоков у Jolt больше нет. Без воркеров (тулы) задача
  выполняется там, где поставлена; `elm_tests` запускает воркеры, как программы.

## Время жизни

- Системы — поля программы: создаются по порядку объявления, разрушаются в обратном. Ссылка на зависимость
  живёт до разрушения системы, потому что зависимость объявлена раньше.
- Объекты сцены сквозь кадры — только хэндлы (`NodeId`, `ModelHandler`); устаревший хэндл даёт `nullptr`.
- Область проекта: окна проекта создаются после открытия и уничтожаются до закрытия — это шаги
  `SwitchProject`, а не договорённость.

## Порядок переделки

Каждый шаг — отдельный коммит, после каждого `elm_tests` и `--editor-selftest` проходят.

1. ✅ `ResourceSystem` и `SceneSystem`. Модуль `resource` (бывший `resmgr`); модуль `model` с `ModelCatalog`
   (CPU-половина `ModelManager`) и `graphics::ModelMeshes` (GPU-половина); `ResourceSystem` в `resource`,
   `SceneSystem` в `Scene`. Пока ими владеет `Engine`; `PlayMode` и `EditMode` работают через `SceneSystem`.
   Модули без циклов: `model` (Model, ModelHandler, ModelCatalog) ниже `Scene`, поэтому `SceneSystem` зависит
   от каталога, а не от всей `ResourceSystem` (иначе `Scene → resource → Scene`).
2. ✅ `GraphicsSystem` (модуль `graphics`): `render::Render` (бывший `RenderSystem`) и render-поток, GPU-меши,
   камера вида и вьюпорт, culling (`OcclusionCulling`), запись моделей (`DrawWorld`), вид на всё окно
   (`PresentToWindow`). Части без суффикса `System`: `Render`, `OcclusionCulling`, `DebugDrawing`. Отличия от
   плана: показ вида — метод `PresentToWindow`, который игра зовёт, а редактор нет, без `GraphicsDesc::presentation`;
   `DebugDrawing` пока у программ (`Editor`, `elm` с `ELM_DEBUG_DRAW`), графика получает только `DebugDraw*` для
   скриптов через `Engine`; мировые трансформы перед `DrawWorld` пересчитывает программа — графика сцену не пишет.
3. ✅ `PhysicsSystem` на `core::JobSystem` (адаптер `CoreJobSystem`, пул Jolt убран). Объединение `PlayMode` со
   `ScriptSystem` перенесено в шаг 4: для него `ScriptSystem` получает сцену и физику в конструкторе, а это и

## Чего нет и почему

| Чего нет | Почему | Когда вернуться |
|---|---|---|
| реестр систем, `ISystem`, `Require<T>()` | наборы известны при компиляции; конструктор проверяет зависимости лучше, чем поиск при запуске | плагины или моды, загружаемые при запуске |
| планировщик фаз, `Before`/`After` | порядок кадра в явной функции читается сверху вниз | систем станет много, а функции кадра — длинными и повторяющимися |
| `DeclareAccess`, параллельные системы в фазе | нет системы, которой это нужно | профайлер покажет, что последовательные шаги — узкое место |
| асинхронная физика | задержка на шаг ради производительности, которая пока не нужна | физика станет узким местом |
| события для всего | задержка и неочевидный порядок; переходы — явные последовательности | появится отправитель, который не должен знать получателей |

## Открытые вопросы

1. **Повтор шести систем в `Game` и `Editor`** — решено: пока два повтора, без общей структуры `Runtime`.
   `elm_tests` — третья композиция, но она не повторяет первые две и `Runtime` ей не нужен: каждый тест
   собирает свой малый набор на стеке функции — сцена и скрипты, сцена и физика, ресурсы без GPU — и именно
   без платформы и графики, чтобы работать без окна и GPU (как сейчас `RunPlayModeTests`). Общий `Runtime` из
   шести систем потащил бы в тесты окно и рендер, а частичные наборы ему не подходят. Поэтому повтор полного
   набора — только у двух программ. Вернуться, если появится третья программа с полным набором.
2. **Имена** — решено: по модулям (таблица в [[#Понятия]]). Глоссарий `CLAUDE.md` правится вместе с каждым шагом
   переделки, а не заранее.
